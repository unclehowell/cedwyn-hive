# Be Ambitious — Cedwyn / Hive skill (v1.1.0)

Adapted from [DannyMac180/skills/be-ambitious](https://github.com/DannyMac180/skills/tree/main/be-ambitious) and Felix Rieseberg’s “How to be more ambitious” (Anthropic, 13 Oct 2026).

**Standing direction for every Hive agent (Grok, Claude, ChatGPT, Tab, Instinct, etc.):**
Before you rewrite, claim or execute any public GitHub issue or private HubSpot correspondence task, FOI draft, catalogue entry, scene, or PR asset, answer the four questions for *this* field, then deepen the exact unit of work. Do not expand scope into a larger project; go one layer deeper on the same deliverable.

## The four questions (always)

Apply these four questions in a compact preflight. For a small routine task, one precise sentence per question is enough; depth is not an excuse to delay execution.

1. **What would a top professional do here that the current task is not asking for?**  
   (Title researcher / forensic archivist / documentary producer / heritage PR / land-registration solicitor / independent historian of Welsh gentry.)

2. **What is the rawest material they would start from**, instead of already-digested summaries or secondary accounts?  
   (Primary conveyance, valuation map, court transcript, original FOI response headers + body, HMLR title register page, contemporaneous newspaper, oral history recording, exact statutory instrument, original 1974 statement, etc.)

3. **Which specific methods and tools would they use?**  
   (Exact catalogue references, OS map series, sequential title search, red-team contrary evidence, independent source verification, statistical or chronological reconstruction, scene bible evidence map, Printify product mock from verified image, etc.)

4. **What, other than you or the model, would show the result is right?**  
   (Live page check, Git commit SHA + redeploy confirmation, GitHub issue/commit timestamp or HubSpot hs_lastmodifieddate for a private correspondence record, outside judge / second agent review, primary document citation that survives challenge, Stripe product live, e-book downloadable, etc.)

Then rewrite the issue prompt / acceptance criteria for public work, or the private HubSpot correspondence task when that is the relevant lane. Leave the revised criteria on the canonical GitHub issue or private HubSpot changelog as appropriate; otherwise execute the deeper version in the same turn.

## Ambition dimensions applied to Cedwyn

### Speed (cycle time without haste)
- Find the shortest reliable path from claim to an accepted result. Reuse existing catalogues, source indexes, task records and cached research; batch independent reads; avoid repeated full scans and duplicate writes.
- Work on one bounded deliverable per seat/check-in. Multiple agents may work in parallel on different tasks, but never have two writers changing the same canonical artifact or frozen draft version.
- If a dependency is genuinely external or owner-only, record the exact blocker and next check, set/retain the correct waiting state, release the job lease and move to another actionable item. Do not idle behind a blocked task.
- Speed never means skipping provenance, no-touch rules, legal/privacy gates, counter-evidence or live acceptance tests.

### Altitude (outcome over task)
- Surface task: “Draft FOI to Glamorgan Archives for Bute X.6(12).”  
  Ambitious altitude: “Close the gap on the 1910 valuation map and X.6(12) so the evidence catalogue and the next documentary scene can cite a verified primary source; produce the follow-on lead list that any agent can pick up.”
- Surface task: “Update wiki page.”  
  Ambitious altitude: “Make the public record self-correcting and transparent so that every new reply is automatically candidates for the catalogue, the snowball metric, and the PR pipeline (ebook chapter, scene, merch, Garden City plant upsell).”

### Depth (expert instruments)
- Insist on the same instruments the best professionals use: original documents before summaries, catalogue references before “the archives say”, exact wording + provenance, versioned “our reading” separate from neutral transcript, contrary evidence kept and shown.
- Unreasonable but reasonable goals: “the gap is closed or its disposition is established”, not “an email was sent”.
- Outside validation: second agent review, live site verification, or primary source that survives red-team.

### Range (multiple fields)
Replace nouns with verbs:  
- “FOI request” → “get the primary document that lets us test Bute’s asserted title and close a catalogue gap”.  
- “Ebook” → “turn verified catalogue entries into a sellable narrative that funds the next archive visit and plants the story in public memory”.  
- “Documentary scene” → “produce a two-minute, source-linked, rights-cleared unit that can be released, merchandised and used as evidence of transparency”.

Assemble the crew mentally: forensic archivist + title researcher + documentary continuity editor + PR/heritage marketer + red-team sceptic. Do what each *does*, do not merely role-play the voice.

## Integration with existing Cedwyn rules

- Still one material step per turn, one signed changelog line, GitHub Issues as public project system of record; HubSpot only for private correspondence, no email send by agents, no private data in public GitHub, research paradigm (Welsh gentry / manorial house, test third-party title from primary records), closed leads, no-idle, claim/lease protocol unchanged.
- The rewrite itself counts as the material step when it produces clearer acceptance criteria or a deeper sub-task that another agent (or the same agent on the next check-in) can execute.
- Apply to every workstream: estate_history, FOI, catalogue, documentary, BIZDEV, website, procurement, Patagonia feasibility, PR (ebooks, Printify, Garden City plants, transparency via public email archive).

## Turn output and downstream conversion

Every public project turn leaves a compact, reusable work packet on the existing GitHub issue; each private correspondence turn leaves its review packet in the appropriate HubSpot task. Include source provenance, decision, test/evidence, unresolved risk and next action.

1. **Outcome:** task ID, one-line deliverable, and why it advances the reconstruction or public value.
2. **Source:** exact artifact/source IDs, original URL or reference, date, retrieval stage, provenance and limitations.
3. **Finding:** what was verified, what is reported by another agent, what is inference, what remains unresolved, and the strongest contrary item checked.
4. **Change:** exact catalogue/page/data/script/scene/ebook/PR or product file changed, with commit SHA or stable artifact ID; do not report a code or website change as live until the deployed page/build is checked.
5. **Independent acceptance:** a test outside the model's own assertion (original document/page image, independent source, second actual reviewer, test suite, live URL, downloadable ebook, product listing check, or other task-appropriate ground truth). Record pass/fail and what would falsify the result.
6. **Next handoff:** one concrete next action or a named external/owner-only blocker.

When a verified finding has downstream value, feed the existing pipeline rather than making a second research silo:
- **Research → catalogue:** preserve the raw artifact and provenance once, add a neutral catalogue record, then link observations and people/place/parcel/event relationships.
- **Catalogue → story:** update the chronology/documentary bible; create a scene package only when the finding materially changes or fills a scene. Keep fact, reported account, reconstruction and dramatic interpretation visibly distinct.
- **Story/research → ebook and PR:** reuse only checked, public-safe material. Ebooks need accurate citations, rights, downloadable-file QA and one clear offer. PR needs a factual press kit and a measurable publication/discovery route, not unsupported claims or mass posting.
- **Approved public material → commerce:** propose Printify designs only from owned/licensed assets; verify current Garden City products, stock and claims before linking. Mockups and drafts are not sales or revenue. No paid listing, purchase, order or spend without the owner's applicable approval.
- **Correspondence → transparency:** record sent messages only from a verified Gmail Sent copy; link replies to the original thread and catalogue attachments once. Keep private correspondence, personal data, legal advice and unverified allegations out of public progress reporting. Existing no-agent-send rule remains in force; an agent's draft is not a sent enquiry.

Do not force every finding into every output channel. One useful verified catalogue update is better than five thin derivative posts. Do not create a new GitHub issue for each downstream format unless it is a genuinely distinct public-safe deliverable with a clear owner and acceptance test.

## Completion and throughput measurement

- Report two separate counts: **CRM closures** (tasks whose status/completion timestamp says COMPLETED) and **accepted completions** (tasks whose own acceptance criteria passed with durable external proof).
- Also measure artifacts newly catalogued, genuine gaps resolved, verified replies ingested, site/build checks passed, scene/ebook/product outputs approved, and blockers released to another job. Never count copies, duplicate IDs, acknowledgement-only replies, task creation, status edits, raw leads or pageviews as completed research.
- Baseline the prior seven days, then aim for at least a 10% increase in rolling seven-day **accepted completions** while maintaining the quality gate. If no trustworthy baseline exists, measure one week first; do not invent a target or lower the standard.
- Each active agent check-in should produce at least one material work step when an eligible job exists. A routing/skip action is operational progress, but is not a completed deliverable. A task is COMPLETED only after its stated acceptance criteria pass; if only part is done, leave it open with the exact next step.
- If the job queue contains work but the agent makes no material change, record why (lease conflict, missing access, owner decision, external dependency, source unavailable or quality failure). Do not hide inactivity behind a long status report.

## Success metric for the skill

More GitHub issues reach CLOSED only with independently verified acceptance, under free-tier Cloudflare/GitHub limits, because each taken job yields a durable catalogue entry, a resolved gap, an approved public output, or a precise next lead instead of a shallow draft.
