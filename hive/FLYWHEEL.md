# FLYWHEEL.md — taking turns on email drafts (any agent)

> **Effective operating rules — Hive protocol v3.27.0 (8 Nov 2026).** `hive/JOIN.md` is authoritative for mailbox release; this document must never weaken it. Historical Gate B thresholds below are superseded by the two-full-round rule.

> **Be Ambitious execution note (v1.1.0, 2 Nov 2026):** before each recipient-facing turn, apply the shared four-dimension preflight (Speed, Altitude, Depth, Range) in `hive/BE-AMBITIOUS.md`. Keep the scope on the exact message and its real purpose: ask for the most useful primary record or clarification, not merely send another email. Read the raw thread and attachments; preserve exact references and contradictions; define what would count as a substantive reply; and ensure the outcome has a catalogue/chronology handoff. When a reply arrives, the flywheel is not complete until it is linked to the original thread, its attachments are preserved/catalogued once, the relevant HubSpot task is updated with evidence, and any resulting research page/scene candidate is routed to the appropriate owner. A draft is not a sent email, an acknowledgement is not a substantive reply, and no agent may send. Existing exact-version, review-quorum, attachment, privacy and owner-send gates remain unchanged.

> **Programme-level authority — Cedwyn Snowball:** before any specialist cycle, read https://cedwyn.bucklerfamily.estate/academy/FLYWHEELS/snowball.md and https://cedwyn.bucklerfamily.estate/projects/. The parent HubSpot task is https://app.hubspot.com/tasks/149419802/view/all/task/536809740513?utm_source=app_12360546_mcp&utm_medium=ai_agent&utm_campaign=task. All specialist work packages are children of that programme in HubSpot. Hive coordinates; HubSpot stores work and decisions; GitHub stores versioned source; canonical evidence has one writer; all other views are derived. The top-level recursive measure is `S(n+1)=S(n)+V+R+G+A+P+B-D-U-W`; report components separately, never count copies, unverified leads or pageviews as historical truth. A suspected legal trigger is private: preserve the artifact, create a confidential HubSpot task, record evidence for and against and what confirms/refutes, then await owner/authorised legal review. Never publish allegations or email counsel automatically. No agent has payment authority or access to private keys/spend-capable wallets; purchases and transfers require explicit custodian approval and limits.

> **Runner liveness:** each active agent must maintain one real recurring check-in in its own harness, titled exactly `Hive check-in — <agent name>`. Target five minutes if that harness supports it; otherwise use the shortest interval actually saved. ChatGPT's harness supports daily, so do not describe this seat as running every five minutes. The Watch cron monitors only; it does not invoke LLMs. `RUNNERS.json` records evidence-backed schedule observations, not seat authority. Check the live roster on every run and never claim a schedule for another seat without direct, current confirmation.

> **One canonical record:** each outgoing email draft is a HubSpot TASK. HubSpot's current subject, first STATUS block, append-only changelog and last-modified timestamp are authoritative. The public GitHub branch carries metadata only. Never put email text, private names, email addresses, phone numbers or private addresses in this repository.

> **Live roster:** read `drafts/ROSTER.json` every time; do not hard-code active or pending agents. Check whether the agent is already active before requesting a seat; an active agent must reuse its seat and must not append a duplicate request. The roster is the sole authority for seat membership.

> **Parallelism:** one writer per draft, many distinct drafts in parallel. Never assign two writers to the same draft/version at once. Use separate active seats for separate live turns; aim to keep useful drafts moving rather than repeatedly routing every stale item to one reviewer. An idle turn may be skipped after more than 30 minutes only when the board, current HubSpot task and live roster support the routing decision. A skip/routing action must not edit recipient-facing text and must not count as a material review.

> **Turn and idle rules:** re-read the complete HubSpot task before acting and verify `hs_lastmodifieddate` immediately before a write. Enforce the four-minute no-touch rule. Respect the task's actual current turn even if public board/baton metadata is stale; HubSpot wins. A skipped turn is not a material review.

> **Source fallback:** before any recipient-facing content change, inspect the complete source thread and attachments, relevant Dartboard lane, QA knowledge base, research/Wayback/projects records, applicable current primary legal/policy sources, and the live `/that-old-chestnut/` and `/dartboard/` overview pages. Mark each material claim VERIFIED, REPORTED BY ANOTHER AGENT, INFERENCE or UNRESOLVED. Do not imply the complete thread, attachments or later correspondence were checked when they were not.

> **Simulated review lenses — non-voting:** when only one actual reviewer is available, that reviewer may apply additional analysis lenses in the same invocation: (1) **Grok-style adversarial challenge** — test weak inferences, counter-evidence, overstatement and the recipient's likely response; (2) **SpaceXSI-style workflow audit** — check request IDs, deadlines, chronology, regime, status/version coherence, attachments and the three-hat/fourth-excuse sequence; (3) **Claude-style editorial/legal pass** — tighten tone, legal precision, structure and adherence to the original question. These are simulations performed by the current reviewer, not actual Grok, SpaceXSI or Claude runs. Never sign a changelog as one of those agents, count a simulated lens as another reviewer identity, create a seat or agreement from it, or use it to satisfy a reviewer quorum. Record the actual executing agent once. SpaceXSI remains pending until its own seat request is verified in the live roster.

> **Full-context email review — owner direction (effective 2 Nov 2026):** for each draft and each exact frozen version, reviewers must complete both full rounds by every required active reviewer seat in the live roster, excluding the author; never count simulations, routing actions, status checks, idle skips or stale-version reviews as approvals. Read the full current dialogue in the source mailbox, including earlier inbound and sent messages, bounce/failed-delivery events and attachments; do not infer a thread exists from a subject line. Decide explicitly whether to send at all, and whether the right action is a new enquiry, a reply in the existing thread or a follow-up. Check the exact To and CC list; identify whether any additional recipient is necessary and why, and do not add a CC by default. Check every attachment and whether a verified, useful map or document is available; do not attach an unverified, irrelevant or sensitive file. Assess whether the questions are focused, complete and useful, what more should be asked, what wording is wise, what claim or detail should be omitted, and the reason for each material recommendation. Compare the request with the live `/that-old-chestnut/` and `/dartboard/` pages and the relevant institution lane so the history, existing dialogue, deadlines, prior requests and project questions stay in context. Verify the recipient's applicable information-access law, statutory coverage and published policy from current official primary sources. Never assume FOIA or EIR applies because an organisation handles records or works with a public body; distinguish statutory requests from ordinary enquiries, archive services, data-subject requests and complaints, and mark unresolved coverage as unresolved rather than making a legal claim. Record the sources, dated findings, recipient/CC and attachment decision, action type, send-or-hold rationale, useful questions, wording risks and reviewer identity in the private HubSpot task against the exact version. Public GitHub and Hive chat may carry workflow metadata only, never private draft text or contact details. A missing legal, thread, attachment or review proof keeps the draft blocked.

> **Historical Gate B — superseded for mailbox release by JOIN.md v3.27.0; retained for historical context only:** routine drafts (FOI/EIR/SAR requests, chasers, acknowledgements and archive enquiries) require at least **3 material reviews by 2 distinct actual reviewer identities** on that exact version. Escalations (ICO, PSOW, IOPC, ICR, ombudsman, preservation/legal notices, internal reviews, complaints) and anything not clearly routine require at least **10 material reviews by 4 distinct actual reviewer identities** on that exact version. Both tiers also require agreement by all required active seats, zero unresolved material defects (`open_issues=0`), `seat_agreements_version` exactly equal to `version`, a completed final three-hat plus fourth-excuse sweep with `final_three_hat_version` matching the version, and verified attachments with `attachments_verified_version` matching the version. Missing or mismatched proof fails closed. Historical `reviews` and `distinct_agents` are informational only; only the current-version counters and recorded proofs count. Never lower the threshold or treat a skip, status check, simulated lens, or stale review as a material review.

> **CSSCPSG pass on recipient-facing text (30 Oct 2026, owner request; prospective):** for versions frozen on or after this protocol update takes effect, a review counts as material only if the reviewer also applies the Grammar House CSSCPSG reading to the draft body: every sentence's actor, act, object and scope must be clear, and every record quoted or relied on is checked against rules S1-S6 (S1 scope, S2 party, S3 agency, S4 term shift, S5 text gap, S6 inconsistency; cedwyn repo branch `csscpsg`, `public/data/model.json` v1.0.0). Any mark and its reason is recorded in the review's changelog line with the rule id. Reviews already recorded on versions frozen before this update stand as recorded and are not invalidated. The v3.27.0 two-round mailbox gate remains mandatory; CSSCPSG adds review depth and does not replace or reduce either round. A CSSCPSG mark is an observation about a record, not a finding of wrongdoing. Draft text, private names and addresses stay in HubSpot; nothing recipient-facing is written to this repository.

No agent sends email; the owner alone sends.

> **Turn completion:** append exactly one changelog line with actual reviewer identity, exact version, local time/time zone, sources actually checked, changes, rejected proposals/reasons, unresolved issues and verdict; keep earlier entries. Sync `BOARD.json` and the relevant `BATON.md` with metadata only, including `version_reviews`, `version_distinct_agents`, `version_agents`, `seat_agreements_version`, `final_three_hat_version`, `attachments_verified_version`, `sent_version`, `last_action_at`, `last_action_by`, `queue_after` and accurate `pct`. Set verification fields only after actually checking the relevant facts. HubSpot wins over stale board/baton fields. WAYBACK requires verified `sent_at`, `archive_url` and `sent_version` equal to `version`.

> **Cadence truth:** the Hive/Watch Cloudflare cron monitors sites and branch changes; it does not invoke reviewer agents. A recurring task in each agent's own harness is what wakes that agent automatically. Report only the cadence actually saved. Each available run should advance one permitted material review or one permitted queue/skip action, then stop.

**TRIGGER CLASSIFICATION — SETUP VS WORK (v3.10.1):** Classify the owner's message first. SETUP is “join hive.bucklerfamily.estate” (including WhatsApp) and follows the onboarding/scheduling rules in `JOIN.md`. WORK includes “Hive check-in”, “Hive check in”, “Hive pass”, or an explicit request to work a Hive queue item. WORK means execute one pass now: read the live contract, roster, board and relevant baton, re-fetch the assigned HubSpot task, obey the no-touch rule, then do ONE material review or ONE permitted queue/skip action. Do not turn a WORK request into scheduler setup or a cadence conversation. If no assigned turn exists, take only a permitted queue action or stop. Never claim a schedule without evidence from that agent's own harness.

**Each recurring run:** fetch the current contract, roster and board; identify this agent's active turn; re-fetch the full HubSpot task; confirm the exact version and last-modified timestamp; perform one meaningful review or queue action; append the signed changelog and update metadata. Do not bulk-scan the CRM unless reconciliation genuinely requires it. Never fabricate independent reviewers or create multiple live assignments for one seat. Honour each connected harness's rate limits. Only Tab creates the single in-thread Gmail draft after all exact-version gates pass; the owner alone sends.

## Dispatcher action (any active seat)

When the board has drafts on a legacy or named turn idle for more than 30 minutes:
1. Re-read the task, board, baton and active roster; verify that a skip is permitted and that the target seat is not already overloaded.
2. Re-prefix only the necessary draft(s) to distinct active seats, one live turn per draft.
3. Append a single skip/routing entry. Do not change recipient-facing text and do not count the routing as a material review.
